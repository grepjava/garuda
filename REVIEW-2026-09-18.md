# Garuda review and capability comparison

Reviewed 2026-09-18 at commit `5fec0bb`.

## Scope and confidence

This is an architecture, capability, and targeted correctness review of the current checkout. It includes package boundaries, framework APIs, transport documentation, connector implementation, streaming, task cancellation, CI, and benchmark methodology. It is not an exhaustive security audit of every parser or of the separately versioned aviancore dependency.

Validation: `swift test` under Ubuntu WSL completed successfully: **927 tests in 109 suites**. Database integration suites are opt-in; this run did not establish interoperability with live PostgreSQL/Redis deployments. Protocol shell/Python suites and performance benchmarks were not run. Findings below are code-inspection findings, not newly reproduced fault-injection failures.

The existing graph was queried but is stale: it still refers to removed `Sources/GarudaHTTP` and `Sources/GarudaQUIC` paths and lacks current Redis vocabulary. Current source and documentation take precedence.

## Assessment

Garuda has substantial application-framework and origin-server breadth. The main shortfalls are production assurance, composability with external async libraries, outbound streaming, distributed application services, and ecosystem integrations. It is much closer to a capable API framework than to a general-purpose reverse proxy or service-mesh data plane.

Existing capabilities must not be mistaken for gaps: typed handlers/extractors, validation, OpenAPI, middleware/groups, CORS, CSRF, sessions, JWT/JWKS and token rotation, authorization policies, PostgreSQL/Redis/SQLite, migrations, streaming requests/responses, SSE, WebSockets, WebTransport, static files, compression/cache support, TLS/ACME, HTTP/1.1–3, request IDs, metrics, reload/drain support, and test clients all have implementation or documented support.

## Correctness and release findings

### P1 — Redis retries can repeat already-executed writes

Evidence: `Sources/Garuda/RedisCluster.swift:247–256,437–440`; `Sources/Garuda/RedisSentinel.swift:143–157,239–246`; `Sources/Garuda/Redis.swift:278–354`.

Both cluster and Sentinel retry on connection closure and timeout without distinguishing failure before transmission from failure after execution. If Redis executes `INCR` and its response is lost, the operation is submitted again. Transactions are also wrapped by the retry paths; losing the reply to EXEC does not imply that its writes were rolled back. Defaults permit five cluster attempts and four Sentinel attempts.

The application can therefore receive a successful result after duplicate side effects. A generic transport error cannot establish replay safety.

Fix: track whether submission may have occurred; return an explicit ambiguous-outcome error for uncertain writes. Permit replay only for known-safe operations or explicit caller policy. Add scripted tests that apply a write, drop the response, and count executions.

### P1 — Pipeline retries replay successful elements

Evidence: `Sources/Garuda/RedisCluster.swift:211–245`; `Sources/Garuda/RedisSentinel.swift:94–101`.

The cluster scans all replies and retries the whole batch if any reply redirects or reports a retryable state. Sentinel similarly turns any failover reply into a retry of the entire pipeline. A pipeline is not atomic. During slot migration, commands on existing and absent keys in the same slot can produce a mix of successful replies and ASK redirects. Replaying all commands repeats completed writes. A single ASKING prepended to a multi-command retry also needs scrutiny because ASKING applies to the next command.

Fix: preserve completed replies and retry only individually rejected commands, with the required ASKING handshake for each redirected command. Treat MULTI/EXEC as a separate semantic case, not an ordinary partially retryable pipeline. Test mixed success/redirect and success/failover responses.

### P1 — Concurrent response producers bypass backpressure

Evidence: `Sources/Garuda/StreamingResponse.swift:85–103,143–160,258–298`.

Each write appends bytes before `settle` checks the backlog. When one producer is already suspended, another finds `writerWake != nil` and immediately returns. That second producer can keep appending while a slow client drains nothing. This contradicts the bounded-buffer expectation stated at the top of the file and matters because concurrent writers are explicitly supported by the API.

Even one producer can overshoot the watermark by the size of one write, so the watermark is not an absolute allocation ceiling.

Fix: serialize admission or use a bounded queue of waiting producers; reserve capacity before copying, and split oversized writes. A slow-reader test with two producers should prove a memory bound and cancellation of every waiter.

### P1 — CI does not automatically protect changes

Evidence: `.github/workflows/ci.yml:1–6` and the complete workflow.

The only trigger is `workflow_dispatch`. Existing protocol integration scripts are not run by this workflow, and PostgreSQL/Redis integration tests require environment variables/services absent from it. A successful manual unit run is useful, but does not establish that changes are continuously checked across real transports and databases.

Fix: run build/unit/compile-fail tests on pull requests and pushes; add service-backed connector jobs and a release/nightly protocol matrix. Keep longer sanitizer, stress, reload, and fuzz work scheduled separately. This is an assurance gap, not evidence that the existing implementations fail those tests.

### P2 — Cancellation is limited to engine-owned waits

Evidence: `Sources/Garuda/HandlerTasks.swift:193–217`; `README.md:606–608`.

Cancellation wakes an engine continuation but does not cancel the reused Swift task. A handler suspended in an external continuation can keep occupying a task slot after its request ends. Enough abandoned external waits can exhaust useful handler capacity, and third-party code relying on Swift task cancellation does not receive ordinary request-scoped cancellation semantics.

Fix: expose a request-scoped cancellation registration/token and supported adapters; bound abandoned external work. Reused task cancellation cannot simply be made sticky across later requests. Tests should cover external waits, child tasks, deadlines, disconnect, and shutdown.

### P2 — HTTP/3 does not have TCP's certificate-selection parity

Evidence: `Sources/Garuda/Config.swift:106–117`; `CONFIG.md:169`.

TCP chooses among configured certificates by SNI, but HTTP/3 always serves the default pair. A hostname covered only by an additional certificate can work over HTTPS/TCP yet fail certificate verification over QUIC. A default SAN certificate covering all advertised names is a workaround.

Fix: implement QUIC SNI selection, or validate and clearly constrain HTTP/3 advertisement/configuration until it exists. This limitation is documented and should not be described as a newly discovered undocumented bug.

## How to interpret competitive position

- **Against Vapor:** protocol breadth is substantial, but Fluent, Leaf, Queues and standard tracing integrations still provide application-development advantages. Avoid comparing only core routing throughput.
- **Against Hummingbird:** prioritize lifecycle/ecosystem integration and predictable Swift concurrency behavior. Its documentation exposes Service Lifecycle; this review does not claim a complete feature-by-feature Hummingbird audit.
- **Against Axum:** typed extraction, responses and middleware already exist here. The larger missing advantage is the composable Tower ecosystem and reusable integration surface. Axum's docs explicitly discuss backpressure limitations too; do not assume another framework solves every overload issue automatically.
- **Against Caddy/NGINX:** Garuda is an application origin with several edge features. Upstream load balancing, proxy behavior and management are still a separate body of work. NGINX Plus features should not be attributed indiscriminately to open-source NGINX.
- **Against Envoy:** a service-mesh/gateway comparison introduces discovery, upstream health/outlier handling, retry budgets and RPC integration. Building these is a strategic expansion, not the next small framework milestone.

## Performance evidence still needed

`BENCHMARKS.md` correctly limits its results to a loopback empty-body route. `HANDLER-API.md` still lists realistic comparisons as unfinished. These results cannot establish overall superiority for production applications.

Add repeatable JSON encode/decode, database round-trip, authenticated request, large upload/download, upstream streaming, TLS/H2/H3, slow-reader, connection-churn and overload scenarios. Record throughput with p50/p95/p99, errors, CPU, RSS and recovery after overload. Use equivalent logging, middleware, worker/CPU limits and correctness settings. Measure application workloads before prioritizing more micro-optimizations.

## Recommended order

1. **Correctness and continuous checks:** safe Redis retries, bounded concurrent streaming, automatic CI, real database and transport gates.
2. **Operational contracts:** external-wait cancellation, deadline budgets, HTTP/3 certificate parity, resource-bound stress tests.
3. **Common application capabilities:** outbound streaming, tracing adapters, durable jobs, distributed quota hooks, supported OAuth/OIDC integration.
4. **Release readiness:** realistic benchmarks, tagged releases, compatibility verification, examples exercising the recommended production integrations.
5. **Optional expansion:** ORM/templates, gRPC, advanced HA connectors, DNS-01 and QUIC resumption. Build a general reverse proxy/control plane only if it is an explicit product goal.

No production source was changed during this review.
